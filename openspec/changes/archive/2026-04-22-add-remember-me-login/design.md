## Context

当前认证链路由前后端共同完成：

- 前端登录成功后将 `accessToken` 与 `refreshToken` 持久化到本地存储。
- 受保护接口默认携带 `accessToken`，返回 `401` 时由前端自动调用刷新接口，使用 `refreshToken` 换取新的令牌对后重试原请求。
- 后端 JWT 中间件仅接受 access token 访问业务接口，刷新接口单独校验 refresh token。

这套链路已经具备“短 access token + 长 refresh token”的基础能力，但还缺少两件事：

1. 登录时无法显式表达“7天免登录”意图。
2. 刷新后如何保持原会话策略没有明确约定。

本次变更横跨前端登录页、用户状态管理、后端登录控制器、JWT 签发与刷新流程，且涉及认证策略与安全边界，因此需要单独设计说明。

## Goals / Non-Goals

**Goals:**

- 为账号密码登录提供显式的“7天免登录”开关。
- 让未勾选与已勾选用户分别使用不同的 refresh token 生命周期。
- 保持现有 access token 校验与自动刷新链路不变，尽量减少对业务接口和路由守卫的影响。
- 确保 refresh token 刷新后继续沿用原会话策略，不因为刷新而意外缩短或放大会话时长。

**Non-Goals:**

- 不将 access token 改成长效令牌。
- 不在本次变更中切换为基于 HttpOnly Cookie 的会话方案。
- 不引入服务端 refresh token 黑名单、单端登录、强制下线等会话治理能力。
- 不调整业务接口的鉴权中间件行为，除非为兼容本次令牌结构变化所必需。

## Decisions

### 1. 使用 refresh token 生命周期承载“7天免登录”语义

“7天免登录”应理解为用户在 7 天内无需重新输入账号密码，而不是让业务访问令牌在 7 天内持续有效。因此：

- `accessToken` 继续保持短期有效，用于受保护接口访问。
- `refreshToken` 根据 `rememberMe` 的值决定有效期。

这样可以复用现有的 `401 -> refresh -> retry` 流程，避免扩大会话泄漏风险。

备选方案：

- 直接延长 access token 生命周期：实现简单，但泄漏后风险更大，不符合现有链路设计。
- 统一把所有 refresh token 改为 7 天：改动更小，但无法表达“是否免登录”的产品选择。

### 2. 登录接口新增 `rememberMe` 布尔字段

前端登录页增加“7天免登录”复选框，登录请求一并提交：

- `rememberMe = false`：签发短会话 refresh token
- `rememberMe = true`：签发 7 天 refresh token

该字段只作用于登录态生命周期，不影响账号密码校验、用户信息返回或路由跳转逻辑。

备选方案：

- 不改接口，仅通过环境配置统一拉长时长：无法满足显式开关需求。

### 3. 在 refresh token claims 中保留会话策略

刷新接口当前只接收 `refreshToken`。如果希望刷新后继续沿用原策略，后端需要能从旧 refresh token 中恢复该策略，而不是依赖前端再次传参。

因此推荐扩展 refresh token claims，记录一个布尔型会话策略字段，例如 `remember_me`。刷新流程按旧 claims 重新生成新 token：

- 旧 refresh token 为短会话，则刷新后仍为短会话
- 旧 refresh token 为 7 天免登录，则刷新后仍为 7 天免登录

备选方案：

- 刷新接口增加 `rememberMe` 参数：前端需要重复维护该状态，且存在客户端随意切换策略的问题。

### 4. 使用配置驱动短会话与长会话时长

建议把 refresh token 生命周期拆成两类配置：

- 短会话时长，例如 `72h`
- 记住我时长，例如 `168h`

这样既保留默认策略的可调性，也让“7天免登录”在配置层有清晰定义，避免未来把固定数值散落在控制器或 JWT 工具函数中。

备选方案：

- 在代码里直接写死 7 天：初期可用，但后续调整策略时需要改代码。

## Risks / Trade-offs

- [风险] refresh token 改为携带更多 claims 后，旧 token 与新 token 的兼容性需要确认
  → 缓解：只在新登录与新刷新路径使用新 claims；旧 token 在部署窗口内按现有逻辑自然过期即可

- [风险] 若刷新时采用“滚动续期”，活跃用户可能长期不需要重新登录
  → 缓解：在需求说明里明确该行为；若后续需要绝对过期时间，再单独扩展 claims 与校验逻辑

- [风险] 前端仍将 token 存在本地存储，无法解决 XSS 场景下的令牌窃取问题
  → 缓解：本次只做会话策略增强，不改变存储介质；后续若提升安全等级，再评估迁移到 HttpOnly Cookie

- [风险] 登录页增加选项后，如果默认值处理不一致，可能导致实际体验和产品预期不符
  → 缓解：在前端表单初始值、接口示例和测试用例中统一默认行为

## Migration Plan

1. 新增前端登录字段和后端接口参数，但保持未传 `rememberMe` 时走短会话默认值，确保兼容旧调用。
2. 扩展 JWT claims 与签发逻辑，让新签发的 refresh token 带上会话策略。
3. 更新刷新接口以从 refresh token claims 继承策略。
4. 更新接口样例和文档，确保联调使用统一字段。
5. 上线后观察登录、刷新、登出链路是否符合预期；如出现异常，可回退到旧的 refresh token 签发逻辑。

## Open Questions

- 未勾选“7天免登录”时，短会话是否继续沿用当前 `72h`，还是收紧到 `24h`。
- “7天免登录”是否采用滚动续期；当前设计默认延续现有刷新模型，即活跃期间可持续延长。
- 是否需要在登录页文案中明确说明“7天内无需重新输入账号密码”，避免用户将其理解为永久登录。
